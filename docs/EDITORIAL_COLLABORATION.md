# 编辑审核协作线程

更新日期：2026-08-16

## 为什么先做这一块

全项目审查显示，账号监控、热点情报、规则、生成、媒体和通知已经形成可运行骨架，但“生成成品 → 团队讨论 → 审核结论 → 交付准备”仍缺少共享上下文。这个断点会让审核意见散落在即时通讯或页面备注里，难以追溯，也无法判断问题是否已处理。

本次设计参考了 Buffer 的草稿审批与 Notes、Sprout Social Smart Inbox 的队列化协作方式，并保留 Hudl Assist 与 Stats Perform OptaAI Studio 所强调的“事实/数据和内容结果可追溯”原则。这里借鉴的是工作流模式，不代表本项目已经接入这些第三方服务。

## 已实现范围

- `editorial_comments` 保存工作区、审核条目、作者、原文、解决时间和解决人。
- 评论原文创建后不可编辑、不可删除；解决状态可以切换，用来表达“待处理/已解决/重新打开”。这样既支持协作，又不重写审计事实。
- 所有读取按工作区和审核条目过滤；创建需要 owner/admin/editor/analyst，解决需要 owner/admin/editor，viewer 只能读取。
- 新增接口：
  - `GET /api/v1/editorial-items/{item_id}/comments`
  - `POST /api/v1/editorial-items/{item_id}/comments`
  - `PATCH /api/v1/editorial-items/{item_id}/comments/{comment_id}`，请求体为 `{ "resolved": true|false }`
- 新增审计动作 `editorial_comment.created` 和 `editorial_comment.resolution_changed`。审计摘要只记录条目 ID、状态和正文长度，不复制正文，避免敏感内容在操作日志中扩散。
- 审核工作台每条目新增“协作”入口，显示按时间升序的线程、作者、状态和时间；具备空状态、加载状态、错误状态和权限降级；评论提交带 CSRF 和工作区标识。

## 数据边界

评论属于工作区内部协作数据，不是外部平台数据，也不改变生成内容的 `source_kind`、事实核验状态或发布状态。审核通过仍只表示内部编辑通过，不能显示为已发布；外部平台发布必须经过对应官方/授权 Adapter 的独立契约验收。

## 下一步路线

### P0：真实环境和可靠性

- 为已实现的平台、RSS、LLM 和通知 Provider 配置有效凭证 canary，记录字段完整率、限流、失败分类和恢复时间。
- 处理 `alembic check` 报出的既有索引漂移：`editorial_saved_views.workspace_id`、媒体生命周期索引；需要单独生成兼容迁移，不与协作评论混合。
- 增加队列和评论线程的指标：未解决评论数、平均解决时长、逾期条目数和审计写入失败率。

### P1：内容操作系统

- 成员邀请、成员状态管理和账号/频道级权限，避免仅靠工作区角色授权。
- 将审核通过内容包关联到事实来源、规则版本、字幕、素材、封面和可用视频片段。
- 建立“待排期”状态和发布 Adapter 契约；在官方授权缺失时只创建待发布任务，不声称第三方发布成功。
- 让订阅告警能一键创建审核条目，并把告警原因、命中指标和来源快照带入协作线程。

### P2：智能化和规模化

- 可信度、新鲜度、来源覆盖和热点生命周期的解释型评分。
- 语义检索的新鲜度、保存查询、召回解释和视频片段/关键帧索引。
- 以真实容量和队列延迟证据决定是否引入更重的基础设施，首期继续保持 PostgreSQL + Redis + Celery 边界。
