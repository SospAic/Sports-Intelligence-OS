## 本轮直接开发

原信息中心的已读标记写入浏览器 `localStorage`，导致换设备、换浏览器或同一工作区的其他成员无法共享处理状态，也无法在服务端验证读回执。本轮新增：

- `inbox_read_states` 表，按 `workspace_id + user_id + item_kind + item_id` 唯一隔离，记录持久化 `read_at`。
- `GET /api/v1/inbox/read-states`：批量读取当前用户对任务/通知记录的读状态。
- `POST /api/v1/inbox/read-states` 与 `/bulk`：单条或批量标记已读，要求 CSRF，重复调用幂等。
- 首页铃铛与 `/notifications` 历史页改用后端读回执；网络失败时只保留临时乐观状态并回滚，不把失败显示成已持久化成功。
- 补充工作区/用户隔离、幂等、批量去重和非法 key 的 API 测试。

这一步只表示“已读/已处理信息记录”，不改变同步任务、通知投递或审核条目的业务状态，也不伪造第三方渠道已完成。

## 行业案例映射

- Sprout Social Smart Inbox 的核心是统一流、筛选、标签、完成状态、团队协作和自定义视图；本项目应把同步、通知、审核和告警逐步汇入一个可操作队列，而不是继续增加孤立的结果页。参考：[Smart Inbox](https://sproutsocial.com/features/smart-inbox/) 与 [功能列表](https://sproutsocial.com/features/)。
- Buffer 将草稿审批、评论 Notes、权限和共享日历放在同一协作流程；本项目已有审核队列和评论线程，下一步应增加邀请/角色、内容日历和“批准≠已发布”的发布状态机。参考：[Collaborate](https://buffer.com/collaborate) 与 [审批草稿](https://support.buffer.com/article/665-managing-and-approving-draft-posts)。
- Hootsuite 的趋势产品强调实时信号、主题聚类、趋势阶段、告警和竞品基准；本项目应让每个热点显示窗口、样本、证据、阶段和下一动作，而不是只突出单一总分。参考：[Trend Research](https://www.hootsuite.com/platform/trend-research)。
- Tubular 强调跨平台统一视图、内容分类和新兴趋势/创作者比较；本项目已有账号横向对比，后续应加入同发布时间窗口、平台覆盖和数据可比性提示。参考：[Tubular](https://tubularlabs.com/)。

## 后续开发方向

### P0：先做真实闭环与可信度

1. **发布与表现归因**：增加 `Publication`、固定窗口 `PerformanceAttribution`，关联生成运行、审核版本、规则/Prompt、实际作品和来源；展示 1/3/6/24/72 小时与 7/30 天表现。没有官方/授权分析时明确显示“需要条件”。
2. **热点生命周期与事件级榜单**：已完成窗口级“同题机会”聚合和 `emerging / accelerating / peaking / declining` 阶段标识；聚合保留算法版本、窗口、呈现数、平台覆盖、去重键和分数口径，但不把启发式同题机会冒充规范事实事件。下一步仍需可靠跨语言实体链接和人工确认。
3. **真实 canary 与 SLO**：为平台 Adapter、新闻源、LLM、通知 Provider 建立每日合成检查，记录字段完整率、限流、失败分类、恢复时间和来源类型；不能用测试 Fixture 代替真实凭证验证。
4. **恢复演练与运行韧性**：当前 `alembic check` 已无新操作；下一步是在备份存储和维护窗口具备后，执行恢复、Redis AOF、Worker 中断和通知超时演练。

本轮已补齐本地可执行部分：`/reliability/slo` 和“可靠性 SLO”页面对内部持久化记录提供带空状态的派生指标，自动化新增只读规则回放接口，`/operations/rights` 提供素材权利核验、证据和审计闭环；外部平台/通知/LLM canary 与生产恢复仍需凭证或基础设施，不能伪造为已完成。

### P1：把运营队列变成内容操作系统

1. **统一收件箱**：加入未读/待处理筛选、标签、保存视图、批量完成、负责人和 SLA；把审核评论、订阅告警和失败任务作为可追踪的队列项。
2. **证据包**：规范人物/球队/赛事实体，把 Article、发布时间、原始 URL、摘录位置、视频、字幕和生成字段连成证据图；生成只能引用冻结证据包。
3. **内容排期与发布 Adapter**：先做排期/待发布状态和权限，再按官方 OAuth/授权接口逐平台验收；禁止在未有 Adapter 时显示“已发布”。
4. **检索可解释性**：保存查询、索引新鲜度、召回来源、结果调试分、结果→选题联动和实际字幕/模型时间段定位已完成；剩余是需要真实素材处理链路的关键帧提取与多模态索引，并需继续遵守真实素材来源边界。

### P2：规模化智能能力

1. 标题/Hook/叙事顺序/缩略图的观察性实验本地闭环已完成；真正随机 A/B、曝光日志和因果分析仍需授权 Analytics 与实验分流基础设施。
2. 受授权 Analytics 数据支持的受众、地域、语言、完播和变现分析。
3. 版权/许可/地域限制/到期时间的素材权利中心（本地闭环已完成，外部版权数据库仍未接入）。
4. 只有容量与延迟证据证明必要时，才引入更重的队列或检索基础设施；当前继续保持 PostgreSQL + Redis + Celery。

## 数据真实性与验收边界

- 公开页可获取指标继续标记 `live` 并完整呈现；私有 Analytics、完播、平均观看时长、流量来源和 RPM 缺少条件时只显示具体所需条件。
- `mock`/Stub 仅用于契约测试，不在生产 UI 中作为真实平台成功；`imported` 必须保留来源文件或 URL。
- 本轮新增读回执是产品操作数据，不是平台数据；它不改变外部同步或通知结果。
- 任何发布、通知发送、真实平台同步和备份恢复仍须在对应权限/凭证和可恢复环境下单独验收。

## 本轮新增开发：能力就绪度诊断（2026-08-17）

审查发现，平台设置页同时展示了适配器能力和凭证状态，但缺少一层“是否可以安全启动工作流”的解释，容易把“环境变量存在”“数据库已配置”“真实 API 可用”“拥有私有 Analytics / 发布权限”误认为同一件事。参考行业 SaaS 的 integration readiness / status page 做法，本轮新增：

- 后端 `GET /api/v1/settings/readiness`，按当前工作区返回平台采集就绪度和跨平台功能边界；只读、不调用外部平台、不回显秘密。
- 新增管理员受保护的 `POST /api/v1/settings/readiness/{platform_key}/probe`：调用已注册 Adapter 的 `health_check`，官方 API 模式优先使用官方平台 Adapter，公开页/会话模式明确标记为适配器运行时探针；结果写入既有 `external_call_attempts` 和审计表，不写入账号/作品数据。
- 平台状态拆为 `待配置`、`已配置·待探针`、`当前受限`；环境凭证回退、工作区加密凭证、适配器实现状态、配置字段和数据来源分别显示。
- 最近一次探针通过后才显示“已就绪”；部分可用、失败、未执行分别保留状态、错误码、耗时和下一动作，避免把 SecretStr 存在或一次性配置成功误报为长期可用。
- 跨平台能力明确列出频道/发布资源权限、私有 Analytics 与 A/B/因果分析、关键帧/多模态索引、文本语义检索的条件和下一动作。
- 设置中心平台管理页新增“能力就绪度诊断”，让运营人员可以在同步前看到缺失条件；“已配置”不会被标成“真实验证成功”。
- 新增后端纯契约测试，覆盖环境凭证已配置但待探针、TikTok API 字段缺失、三项能力阻断和语义检索配置状态。

这项能力解决的是可信度和操作引导，不会伪造平台成功。

## 本轮追加开发：官方 API 自动探针与失败恢复（2026-08-17）

在上述就绪度诊断之上，新增低频官方 API synthetic monitoring：

- Celery Beat 每小时调度一次；实际执行仍按 `SIO_PLATFORM_CANARY_INTERVAL_SECONDS`（默认 3600 秒，范围 15 分钟至 24 小时）去重，避免 Beat 重启或重复投递造成探针风暴。
- 只对已配置且可解析的 `api` 凭证执行；`public_page`、`authorized_login` 和 `authorized_session` 不会被后台任务自动触发，保持授权、条款和会话边界。
- 结果继续写入 `external_call_attempts` 和审计表，追加 `trigger=scheduled`，设置页显示最近一次探针是自动还是手动、时间、状态、耗时、错误码和安全详情。
- 失败/降级只在状态转变时创建一个 `platform.canary_failed` 内部运营事件；持续失败不重复刷屏，恢复后把同一事件标为 `resolved`。未配置通知渠道时不伪造外部发送，内部事件是唯一事实记录。
- 配置项和任务说明进入运行时设置、`.env.example`、Compose 与测试；不需要新增迁移，复用既有外部调用和系统事件模型。

这一步参考了 Datadog/PagerDuty 常见的合成监控、状态转变告警、去重和恢复闭环，也延续 Sprout Social Smart Inbox 将告警纳入可操作队列的方向。容器内目标回归已通过 `13 passed, 1 warning`；Docker Desktop `29.7.2` / Compose `v5.3.1` 已完成镜像重建、Compose 更新、迁移无漂移、API/Web 健康和登录入口验收；手动触发自动任务无错误，但因当前平台配置均不是 `api + configured`，任务安全跳过 4 个目标，没有发起未经授权的外部调用。仍未完成的是配额/字段完整率、新闻/LLM/通知 Provider 的真实 canary，以及已配置通知渠道后的外部升级投递。
