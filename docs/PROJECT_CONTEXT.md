# Sports Intelligence OS 项目长期上下文

更新日期：2026-07-25

## 1. 产品使命

Sports Intelligence OS 将多平台体育账号表现、作品增长、新闻热点、叙事规则、Prompt 工作流和实时通知放进一个可审计的操作系统。目标用户可以发现事件、判断价值、生成内容、监控结果并自动响应，而不需要把多个数据工具和零散 Prompt 手工拼接。

核心用户：

- 体育短视频创作者：寻找选题、核实事实、生成无真人出镜的解说内容并复盘表现。
- 体育内容运营者：跟踪多个账号、事件与平台，建立选题和发布节奏。
- 多平台账号管理者：比较账号/作品表现，对异常增长和热点进行自动化响应。

## 2. 核心业务能力

### 2.1 账号监控中心

首期平台范围包括 YouTube、TikTok、抖音、Bilibili，并为 Instagram、Facebook、X、Threads、快手、小红书等预留适配器扩展边界。

账号级数据包括粉丝数、关注数、总播放量、总点赞量、总作品数，近 7/28/30/90 天增长，发布频率、平均/中位播放量、平均互动率、爆款率和历史曲线。

作品级数据包括作品 ID、标题、描述、发布时间、时长、播放、点赞、评论、分享、收藏、新增粉丝、平均观看时间、完播率、流量来源、搜索关键词和平台可用扩展字段。每次采集保留历史快照，以计算指定时间段增长量、增长速度和增长加速度。

用户需要多账号、多平台、多层级排序、多条件筛选、自定义指标、历史趋势、账号/作品对比和数据导出能力。平台没有提供的指标必须标记为“不可用”或“推算”，不得伪造为原始数据。

### 2.2 体育新闻与热点中心

数据源包括主流/体育媒体、官方体育组织、联赛与赛事官网、球队或运动员官方渠道、RSS、新闻/搜索 API、社交热点、视频平台热门内容和用户自定义源。

首期面向综合体育，重点覆盖奥运会、田径、足球、篮球、棒球、NFL、F1、UFC、网球、冬季运动和综合体育争议事件。

标准字段包括标题、摘要、正文、来源、原始链接、发布时间、抓取时间、事件发生时间、项目、赛事、人物、队伍、国家、语言、热度、时效性、可信度、来源等级、重复/更新报道标识、短视频适配度、素材可获得性、争议度、视觉冲击度和故事反转度。

系统支持最新/热度/来源排序，时间段与体育项目筛选，人物/赛事/队伍搜索，多来源事件聚类、去重、事件时间线和热点趋势。评分应保留算法版本和解释。

### 2.3 规则与 Prompt 中心

规则集合和 Prompt 集合支持版本、草稿/发布状态、启停、优先级、标签、分类、测试、回滚、导入导出、差异比较和修改历史。

首个核心规则集合来自 `ELITE_SPORTS_FACELESS_NARRATION_ENGINE_V7_9_LATE_CAUSE_REVEAL_REACTION_RELAY_ANSWER_WORD_PROTECTION_FULL.txt`。必须同时保留不可变原文与结构化表示。结构化层级至少支持章节、子章节、规则、说明、Why、How、Good Example、Bad Example、QA Check、Rewrite Instruction、优先级、强制性、适用运动、故事类型、输出类型、依赖规则、冲突规则、标签和版本。

7.9 叙事约束的长期摘要：

- Hook with force；在叙事赢得 Reveal 前保护答案词；悬念决定顺序，体育决定语言。
- 每句只承担一个主要功能，句间通过因果、对比、时间或结果连接。
- 使用自然美式口语和专业体育词汇，只解释理解故事所必需的信息，尽快回到具体比赛动作。
- 默认结构为 Hook → Misdirection → Contradiction → Reveal → Result。
- 默认约 1200–1250 英文字符；输出不换行美式英文 TTS、中文翻译、含 Emoji 标题、大写关键词、视频搜索词、素材建议和十个中文字以内的工程文件名。
- 事实需要联网核实；不得为了戏剧性改变事实；必须按事件事实重组而非机械改写；Reveal 前不得泄露关键答案词；适用于无真人出镜体育解说。

原文未导入前，这份摘要不能替代原始规则文件，也不能被宣称为完整 7.9 规则。

### 2.4 内容生成中心

输入可来自账号、作品、单条新闻、热点事件、多新闻聚合事件、手动事件，以及用户上传的字幕、文案或文件。用户可选择规则/Prompt 集合、模型、输出语言/格式/长度、运动、叙事风格、联网核实，以及标题、翻译、素材搜索词、SSML、SRT、标签和自动审查重写选项。

标准流程是：Research → Fact Extraction → Event Timeline → Story Qualification → Draft → Editorial Review → QA → Rewrite → Final Output。每次运行记录输入、规则/Prompt 版本、模型与参数、原始输出、审查、重写、最终结果、Token、耗时、成本、评分和采用状态。

### 2.5 规则引擎与自动化

条件覆盖指标阈值、时间窗增长、分享率、粉丝变化、新闻热度/新鲜度/可靠来源数量、增长加速度、关键词热点、突发项目、流量来源结构和自定义爆款指标。

表达式支持 AND、OR、NOT、比较、包含/不包含、正则、时间窗口、环比、对历史均值、连续满足、冷却和去重。

动作包括系统提醒、邮件、通用 Webhook、Telegram、Discord、Slack、Microsoft Teams、飞书、钉钉、企业微信、PushPlus、Server 酱、Bark、自定义通知、内容生成、保存选题、创建任务和外部 API。首期统一通知接口至少完整实现邮件、通用 Webhook、Telegram、Discord、飞书、钉钉和企业微信；其他渠道以插件扩展。

## 3. 首期垂直切片

第一次交付必须可启动、可登录、可操作，至少包括：

- 用户登录；
- 添加平台账号；
- YouTube 官方 API Adapter 和明确标识的通用 Mock Adapter；
- 账号列表/详情、作品列表/详情、数据快照、手动/定时同步；
- RSS 新闻源、新闻列表/详情和基础去重；
- 7.9 规则原文导入、结构化展示、编辑和版本保存；
- Prompt 模板管理和一个完整内容生成工作流；
- 一个自定义监控规则；
- 邮件或 Webhook 推送；
- 系统事件日志；
- Docker Compose 一键启动；
- 基础测试和中文 README。

“可操作”意味着至少一条真实配置路径或明确的 Mock 开发路径贯穿 UI、API、持久化和后台任务；纯静态界面不算交付。

## 4. 非功能要求

- 安全：凭证只从环境变量或安全存储读取；日志脱敏；遵守平台条款和访问控制。
- 可靠性：外部调用有超时、重试、退避、限流、幂等和错误记录。
- 可追踪：数据来源、规则版本、Prompt 版本、模型参数、任务和通知均可审计。
- 可扩展：平台、新闻源、LLM、通知使用独立契约和注册机制。
- 可部署：首期单机 Docker Compose，区分开发与生产配置。
- 可维护：迁移、类型检查、格式化、测试和文档纳入阶段验收。
- 可访问：清晰的空状态、错误状态、加载状态和键盘可用性。

## 5. 范围边界

首期不主动引入 Kubernetes、Kafka、ClickHouse 或 Elasticsearch。只有基于实际容量或可靠性证据，才通过架构决策记录引入重型组件。

首期不要求一次实现所有平台、新闻源、LLM 或通知渠道；但扩展接口必须真实可用，且已实现/未实现状态必须准确。

非官方采集必须标记来源与合规风险。Playwright 仅用于无需绕过验证或访问限制的合法公开页面。
