# Sports Intelligence OS 全系统审计与可行性分析

日期：2026-08-14
审计对象：账号监控、作品数据、媒体/字幕、热点情报、评论、自动化、通知、内容生成、运维与部署链路
审计方式：代码审查 + 前端真实页面检查 + Docker 运行态检查 + 自动化测试 + 行业公开产品能力对照

## 一、结论先行

当前系统已经具备“单机可运行、真实数据可追溯、核心账号/作品监控可用”的产品基础，作品详情页的媒体状态与字幕语言覆盖本轮已经补齐。以当前代码和验证证据判断：

| 维度 | 当前评级 | 结论 |
| --- | --- | --- |
| 作品详情与媒体操作 | A- | 已下载/已生成状态可识别；本轮页面实测视频、字幕、info.json 均正确置灰 |
| 字幕展示与本地翻译 | B+ | 原字幕、双语展示、时间轴、逐词高亮和本地翻译队列已形成闭环；真实翻译任务已成功 |
| 账号同步可靠性 | B | 已有增量、重试、进度日志和数据保留规则；仍需要各平台真实账号的持续 canary 与更强的产物完整性检查 |
| 热点情报 | B- | 已有趋势采集、窗口筛选、分类和日志；距离“全网 24–72 小时热点雷达”还缺更多实时源、去重、评分和新鲜度控制 |
| 自动化与通知 | B | CRUD、启停、失败投递和审计链已验证；尚未向真实第三方渠道发送消息，不能宣称外部交付已验收 |
| 数据分析 | B- | 公开指标与派生指标边界清楚；官方私有分析、流量来源、留存和收入仍需 OAuth/API 授权 |
| 工程质量 | B | Web 构建、类型检查、74 个前端测试通过；API 全量套件此前在 20 分钟门禁内超时，仍需拆分和提速 |
| 高可用性 | C+ | 单机 Docker Compose 可用，但 PostgreSQL/Redis/worker 尚未形成跨主机故障切换和独立任务恢复体系 |

总体判断：不建议现在重写全部系统，也不建议立刻扩展到“全平台发布/全网无限抓取”。最有价值的下一阶段是先建立统一的“产物状态 + 采集质量 + 来源新鲜度 + 任务 SLO”基础，再按平台合规能力逐个增加真实源。

## 二、本轮证据与边界

### 已验证的真实运行证据

- 浏览器打开真实作品 `The Sound That Sent MLB Players RUNNING`：第一语言自动选择 `en`，第二语言自动选择 `zh`；视频、字幕、info.json 都显示“已下载”并禁用按钮；八种本地生成语种全部覆盖时，生成按钮显示“已生成字幕”并禁用。
- 本地翻译服务根因修复后，真实 `subtitle-worker` 任务完成 7 条翻译轨道，7 次请求均 HTTP 200，`translation_errors=[]`，任务状态 `succeeded`，页面能看到滚动日志和生成结果。
- Web Docker 生产构建通过，Next.js 路由全部生成；Web TypeScript 通过；最终前端回归为 20 个测试文件、74 个测试通过；Web ESLint 0 errors、12 warnings。
- 账号数据保留、增量媒体合并、评论非破坏性刷新和同步防卡死的定向 API 回归此前为 31 passed；字幕翻译/时间轴/工具定向回归为 11 passed。
- 账号同步、自动化、通知、热点、作品详情等前端路由和主要 CRUD/异步任务的浏览器验收证据见 `docs/FULL_SYSTEM_TEST_REPORT-2026-08-14.md`。

### 不应被误判为“已完成”的边界

- YouTube/TikTok/Bilibili 的真实平台行为会受登录墙、Cookie、代理检测、验证码、地区和限流影响；测试环境没有用假数据覆盖这些失败。
- 通知渠道的前端配置、加密存储、失败投递和重试记录已验证，但本轮没有向真实外部 webhook/IM/邮件地址发送消息。
- “24h 播放增量”只有在存在历史观测快照时才是观测差值；没有足够快照时不能当成平台原生实时值。
- 媒体按钮当前依据数据库媒体清单判断“已下载”，并不等于已经完成文件存在性、大小、可读性和校验和检查；这是下一阶段的 P0 改进项。

## 三、与优秀产品的能力对照

### 1. YouTube Studio：分层指标和可解释的分析入口

YouTube 官方把频道/视频分析拆成 Overview、Content、Reach、Engagement、Audience、Revenue 和 Trends，并提供实时/典型表现、比较和导出能力；官方还强调不要只看一个指标，应把多类指标组合后再判断内容表现。

对本系统的启示：账号概览、作品详情、趋势和派生指标必须共享同一份快照/指标口径；每个指标要显示 `observed / derived / requires_authorization`，并显示快照时间、来源和计算窗口；继续保留官方授权条件态；下一阶段增加同平台同内容类型比较和 CSV/JSON 报告导出。

参考：[YouTube Analytics 官方入门](https://support.google.com/youtube/answer/9002587)、[YouTube Studio Dashboard 官方说明](https://support.google.com/youtube/answer/2673341)

### 2. TikTok Studio：内容、分析、评论和趋势在一个工作面

TikTok 官方说明 TikTok Studio 同时提供内容上传/管理、内容表现分析、评论管理、趋势/灵感和部分变现数据，并指出部分能力依赖地区、账号条件或 Web/移动端差异。

对本系统的启示：作品详情不应只是一张指标表，媒体、字幕、评论、素材和下一步动作应有统一状态；评论保留作者、发布时间、点赞、回复、来源和采集时间的方向正确，下一步是增量游标和评论变化追踪；平台不开放或要求授权的字段继续显示条件提示，不绕过登录/安全机制。

参考：[TikTok Studio 官方创作者工具说明](https://support.tiktok.com/en/using-tiktok/creating-videos/creator-tools-on-tiktok)

### 3. Meta Business Suite：内容级触达/互动和团队操作

Meta 官方说明帖子发布后即可看到 reach 和 engagement，并可在 Meta Business Suite 的 Insights/Content 中查看帖子和故事的详细洞察。

对本系统的启示：平台差异应落在 Adapter/Provider，不应让前端用平台名称写大量分支；账号、作品、评论、任务和通知都要携带权限、来源和更新时间；若未来增加发布能力，必须先建立账号权限、草稿、审批、失败补偿和平台回执模型。

参考：[Meta 官方帖子洞察说明](https://www.facebook.com/help/131809553587433)

### 4. Hootsuite/同类社交情报平台：监听、基准、告警和报告

Hootsuite 的公开产品能力把跨网络发布、互动、分析、社交监听、情绪、竞品基准、自定义报告和实时告警组合在一起；其产品页面也明确说明不同平台原生数据的更新频率不相同。

对本系统的启示：热点情报中心应定位为体育领域实时情报管线，而不只是从本地存量作品做排序；每个热点必须有来源集合、首次发现时间、最后抓取时间、事件时间、热度分数、置信度、去重簇和新鲜度衰减；告警需要阈值、时间窗、来源质量和重复抑制；报告导出、定时报告和竞品/账号基准是比继续堆叠图表更值得的扩展。

参考：[Hootsuite 平台能力](https://www.hootsuite.com/platform)、[Hootsuite Analytics](https://www.hootsuite.com/platform/analytics)、[Hootsuite Listening](https://www.hootsuite.com/platform/listening)

## 四、按模块的全面审计

### A. 账号监控与同步

已完成/可用：账号详情、同步入口、同步运行记录、实时滚动日志、分页/窗口化目录和错误码链路已经存在；已有作品不会因为新一轮空结果、稀疏评论或缺失媒体清单被覆盖；公开页面优先、API 增强、授权字段条件提示和 `live/imported/mock` 来源边界符合项目基线。

仍需完善：

1. 同步质量状态增加 `complete / partial / stale / blocked / degraded` 和字段级缺失原因。
2. 产物完整性检查文件存在、大小、MIME、可读性、checksum、最后校验时间。
3. 为 YouTube、TikTok、Bilibili、抖音各保留一个小样本公开账号，按日验证目录、封面、指标、详情和错误类型。
4. 在任务详情中显示实际并发度、请求预算、账号间隔、重试次数和超时。
5. 长同步支持暂停/取消/继续，并以账号+平台+外部作品 ID 做幂等键。

### B. 作品、媒体与字幕

已完成/可用：视频、字幕、原始 info.json 的已下载状态已经进入按钮层；本地字幕生成按语言覆盖检测；默认英语/中文；`und-auto` 在产品界面显示“源字幕”；字幕展示框、视频联动、时间戳开关和导出格式保持可用。

仍需完善：引入 Artifact Registry 区分 `ready/missing/corrupt/stale`；列表区分平台人工字幕、自动字幕和本地翻译；媒体文件和 info.json 保存同一下载任务版本/来源 URL；翻译服务、模型、磁盘容量和队列积压显示在设置页；缺少 word timing 时继续句级高亮并说明原因。

### C. 热点情报中心

当前已有 24/48/72 小时窗口、体育分类、平台筛选、排序、指数/矩阵/时间线、采集任务和悬停日志。若目标是“全网抓取当下 24–72 小时热点新闻、作品和视频”，仅依赖现有平台存量作品和有限新闻源不够，采集应拆成：

`Source Adapter → Raw Item → Canonical Event → Dedup Cluster → Freshness/Heat Score → Alert/Report`

优先接入官方 RSS/API、赛事官网、球队/运动员官网、主流体育媒体和合规公开趋势源；增加跨语言实体归一化、跨源事件聚类、热度增长速度、来源可信度、跨源确认数、发布时间衰减、内容可获得性、事件告警和重复抑制。

### D. 评论 Top 20

保存平台评论 ID、作者、文本、点赞、回复、发布时间、来源和采集时间的方向正确。下一步使用分页游标/时间水位，保存评论快照并计算点赞/回复增长，增加语言/情绪/主题标签，同时保留原文、模型版本和公开/授权/不可用状态。

### E. 自动化、通知与运维

自动化 CRUD、启停、动作绑定、通知渠道加密脱敏、失败投递、重试、任务/调用/死信/日志页面已经形成闭环。仍需真实渠道 delivery canary、通知幂等键、去重窗口、渠道限流、指数退避、死信重放，以及从触发事件反查条件计算和最终投递的完整链路。

### F. 内容生成、规则和多语种能力

规则版本化、结构化编辑、内容生成工作流、字幕素材接入和 Provider 条件禁用已存在。仍需生成阶段恢复、模型/Prompt/数据快照、成本统计、ASR/翻译 CPU/GPU 预算、磁盘清理、源轨道 checksum、时间轴版本和质量标记。

### G. 数据库、任务和高可用

单机 Compose 适合开发、验收和小规模内部使用，不等于跨主机 HA。建议先拆 API 测试分片，加入任务/外部调用/队列积压/同步耗时/产物成功率/通知成功率指标，再做租约、心跳、幂等和可恢复状态机；达到数据规模阈值后再做数据库分区、对象存储和历史归档，不应提前引入 Kafka/ClickHouse/Kubernetes。

## 六、优先级路线图

### P0：先让“已同步”可信

- 引入统一 Artifact Registry：`pending/running/ready/missing/corrupt/stale/failed`。
- 所有下载/生成按钮基于产物状态，而非单纯非空字符串。
- 同步任务增加账号锁、任务租约、心跳、取消、恢复和每平台预算。
- API 全量测试拆分为并行分片，门禁中保留慢测试报告。
- 账号页显示最后成功同步、部分成功字段、失败原因和下一次计划时间。

### P1：扩大情报价值

- 热点中心接入首批高价值实时源，构建跨源事件聚类和新鲜度评分。
- 评论增量、评论变化、主题/情绪标签和评论告警。
- YouTube OAuth 私有分析和真实通知 canary。
- 翻译服务健康面板、队列容量、缺失语种重试和质量/模型版本。
- 导出统一的账号、作品、热点和通知报告。

### P2：规模化和高可用

- SSE/WebSocket 任务状态、跨页面统一任务中心。
- 对象存储和媒体生命周期管理；数据库分区/历史快照归档。
- PostgreSQL/Redis/worker 冗余、故障转移和灾备演练。
- 竞品基准、最佳发布时间、审批协作和多角色权限。
- 合规前提下再评估发布、评论回复和跨平台内容编排。

## 七、生产验收门槛建议

在把系统称为“高可用生产系统”前，至少应满足：

1. 连续 7 天平台 canary 无未解释的成功假象；失败均能归因到平台、凭证、限流、网络或代码。
2. 普通账号在预算内完成同步，长账号持续输出进度且不无限等待；失败任务可恢复，不产生破坏性覆盖。
3. 产物就绪率、字幕语言覆盖率、翻译成功率、通知成功率都有可查询历史指标。
4. 所有派生值带窗口、公式、观测时间和置信度；公开原始指标与推算值绝不混淆。
5. 真实通知、数据库恢复、队列恢复、磁盘不足和平台登录失效均完成演练。
6. API 全量测试在稳定门禁内完成，或明确拆分为快速门禁 + 夜间完整套件，并持续追踪慢测试。

## 八、最终建议

当前最稳妥的产品策略是把系统定位为“体育内容监控与情报工作台”，先把同步正确性、产物可信度、热点来源质量和任务可观测性做成优势；不要用大量平台发布功能掩盖监控链路的不确定性。现有架构足以支撑这一方向，下一步重点是补状态机、完整性检测、来源扩展和 SLO，而不是推倒重写。
