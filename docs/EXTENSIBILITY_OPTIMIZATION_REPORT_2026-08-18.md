# Sports Intelligence OS 可扩展与可优化评估报告

日期：2026-08-18
范围：前端工作台、FastAPI 领域服务、平台适配器、Provider、Celery/Redis、热点情报采集、数据来源与部署验证。

## 一、结论摘要

项目已经具备继续扩展的基础：平台采集、新闻源、LLM、通知、翻译和任务执行均有独立注册边界；热点榜单也已经从静态展示改为真实数据、证据链和去重后的机会索引。

当前最值得投入的方向不是继续增加孤立页面，而是把“能力目录、数据契约、采集覆盖、运行时状态和权限边界”统一为机器可读的产品契约，并由同一份契约驱动 API、前端检查和自动化测试。本轮直接落地了两项高收益基础能力：

1. 建立可版本化的体育热点采集目录：50 个主流项目 + 30 个一般项目。主流项目每项目标 50 条，一般项目每项目标 10 条；不足时仅报告真实 Provider 返回上限。
2. 修复界面语言切换只修改 `html.lang`、而不改变界面文案的问题。现在语言偏好由统一上下文驱动，导航、搜索、同步/未读信息中心、用户菜单和语言选择器会实时切换，偏好继续保存在当前浏览器。

## 二、现状评估

### 1. 架构与扩展性

优点：

- 平台差异集中在 `PlatformAdapter` 和注册表，业务服务不需要为每个平台复制完整流程。
- LLM、新闻和通知 Provider 有独立生命周期、超时/重试和错误分类边界。
- 设置页已经具备配置检查、平台能力矩阵、探针和真实/未验证状态区分。
- 数据实体保留 `source_kind`、`provider`、`external_id`、`fetched_at` 等来源信息，符合可审计数据边界。
- Celery 任务、外部调用记录、死信和通知投递形成了可继续扩展的异步执行骨架。

主要风险：

- 原有 Provider 的能力元数据不完全统一，扩展新 Provider 时容易出现“代码已经注册、UI 没有能力说明”的漂移。
- 热点采集的项目维度此前只有少量分类词，无法表达“覆盖哪些体育项目、每个项目采集了多少真实样本”。
- 前端功能清单、配置检查和部分领域状态仍存在局部重复定义，后续增加功能时需要继续加强契约门禁。
- 目前平台级 Analytics、频道/发布资源权限、关键帧多模态索引仍受外部授权或基础设施限制，不能用派生指标替代真实能力。
- 语言选择之前只有本地存储和根节点 `lang` 属性，没有翻译资源和渲染上下文，因此用户会看到“选择成功但界面不变”。

### 2. 数据与热点情报

- YouTube 之前只有全局热门视频和一个泛体育搜索，项目粒度不足，且搜索结果缺少逐项目的覆盖目标。
- RSS/Atom 适合补充新闻证据，但不能证明播放量、点赞、评论等平台指标；这类字段必须保持 `null` 并展示来源边界。
- 同一视频可能出现在多个项目搜索结果中，若不在采集轮次内按 external id 去重，会放大榜单热度。
- “体育大类/媒体名/平台噪声”过滤规则已经存在，但体育项目词表和采集目标仍需独立版本化。

## 三、本轮已直接开发

### A. 体育热点 50 + 30 采集契约

新增 `apps/api/app/services/sports_catalog.py`：

- 50 个主流项目：足球、篮球、网球、棒球、板球、游泳、田径、赛车、冰球、冬季项目、格斗项目等。
- 30 个一般项目：五人制足球、沙滩项目、卡巴迪、板式网球、匹克球、斯诺克、飞镖、漂移、牛仔竞技等。
- 每个项目拥有稳定 key、中文名、英文搜索词、项目层级和默认目标量。
- 目录带有 `sports-hotspot-taxonomy-v1` 版本号，并在模块加载时校验 50 + 30 数量，避免无意减少覆盖范围。

采集行为：

- YouTube 官方 API 按目录逐项目调用 `search.list`，使用英文项目搜索词、美国区域、近 30 天、按播放量排序，随后使用 `videos.list` 获取官方统计。
- 主流项目默认目标 50 条，一般项目默认目标 10 条；均受 YouTube API 单次最多 50 条约束。
- 同一轮按视频 external id 去重；同一视频不会因命中多个搜索词而被重复写入。
- 每个项目记录 `target_items`、`actual_items`、`status` 和来源。状态为 `met`、`limited_by_source`、`failed` 或未配置，不使用占位记录补齐。
- `SIO_HOTSPOT_SPORT_QUERY_CONCURRENCY` 默认 3，避免 80 个查询同时打满 Provider；目标量和并发均可通过配置调整。

新增接口：

`GET /api/v1/trends/sports-catalog?window_hours=24`

接口返回 80 个项目的目录与当前时间窗真实覆盖情况。热点页面新增“体育项目采集覆盖”面板，可查看 50/30 数量、目标量、达标数和逐项目实际返回量。

### B. 界面语言切换修复

新增 `apps/web/lib/ui-i18n.tsx` 并在应用 Provider 层挂载：

- 语言状态、`document.documentElement.lang`、`data-ui-language` 和翻译函数由统一上下文维护。
- 语言切换器不再自己维护第二份状态，避免选择器状态与页面状态分离。
- 已提供中文、英语、日语、韩语、西班牙语、法语、德语、葡萄牙语的核心工作台文案；英文优先覆盖侧栏导航、全局搜索、同步状态、未读信息中心、用户菜单和设置入口。
- 其他业务页面仍会逐步迁移到 `t()` 契约；未迁移文案会安全回退为中文，不会出现空白或错误 key。

## 四、后续扩展优先级

### P0：能力契约与真实数据闭环

1. 将平台适配器、LLM、新闻和通知 Provider 的 descriptor 统一成一个只读能力目录，自动输出实现状态、配置字段、来源类型、健康探针和下一步动作。
2. 为热点采集增加配额预算、API 429 处理、每项目最近一次成功时间和数据新鲜度 SLO；80 项查询应支持分批执行与断点续采。
3. 把“采集目标”与“榜单展示数量”分离。目标量用于采集覆盖，页面分页用于阅读体验，不能因 UI 的 20 条分页而误判采集不足。
4. 为所有主要数据实体增加统一的 freshness、evidence_count、source_scope 和 coverage_status 字段，并继续保持 live/imported/mock 明确区分。

### P1：行业级运营能力

1. 频道级 / 发布资源权限：建模平台 OAuth scope、资源 external id、授权对象、发布回执和撤销时间。
2. 内容发布编排：草稿、审批、定时、上传、平台处理、发布完成、失败重试使用统一状态机和幂等键。
3. 统一收件箱：同步、任务、通知、平台告警都进入同一事件流，提供去重、已读、跳转和历史检索。
4. 热点实体图：人物、队伍、赛事、联赛、地点和新闻事件建立稳定实体，排行榜按实体聚合而不是按原始词重复计数。
5. 证据包导出：每个热点保存来源 URL、发布时间、抓取时间、平台指标和算法版本，支持审计和编辑交接。

### P2：高级分析与多模态

1. 私有 Analytics：在取得平台 OAuth scope 后，加入流量来源、留存、受众和变现字段；未授权时继续显示明确条件。
2. A/B 与因果分析：先完成曝光、分流、转化、实验版本和预注册假设，再扩大统计模型，不能把观察性对比宣称为因果结论。
3. 关键帧与多模态索引：先落地媒体 artifact、ffmpeg/PyAV 时间戳、模型/版本和可重建任务，再接入多模态向量检索。
4. 本地化：把剩余业务页面按页面清单迁移到统一 `t()`，优先完成设置、热点、下载、账号和生成工作流；翻译资源必须可测试、可回退、不可由用户输入拼接 HTML。

## 五、验收标准

- 新增体育项目必须只修改目录，不在采集器、路由和前端复制平台分支。
- 每次采集结果必须能回答：项目是什么、目标多少、实际多少、来自哪个 Provider、何时抓取、为什么不足。
- 真实 API 不可用时，页面显示未配置/失败/不足；不得用 Mock 成功或静态数据填充达标数。
- 语言切换至少验证：选择器文案改变、核心导航改变、根节点 `lang` 改变、刷新后偏好保持。
- 任何后续代码修改都必须执行项目约定的 Docker 镜像重建、Compose 更新、健康检查、迁移检查和对应自动化测试。

## 六、已知限制

- 当前主流/一般项目的 live 达标情况取决于 YouTube Data API Key、配额、地区和实际搜索结果；代码不会宣称无凭证时已经采集成功。
- 80 个项目的完整官方 API 查询会增加配额消耗，后续必须补充配额预算和断点续采，生产环境不应无限频繁手动点击采集。
- 本轮语言切换先完成全局工作台核心文案；业务页面的逐字段翻译是下一阶段工作，中文回退是有意设计而不是伪装成全量翻译。
