# 热点体育项目采集策略评估与扩展方案

日期：2026-08-18

## 结论

热点项目的达标问题，优先级应是“扩充可信来源”，其次才是“增加单一来源的检索数量”。只提高 YouTube 单一查询的 `maxResults` 会带来三类副作用：相同视频跨项目重复、API 配额快速耗尽、搜索结果把“相关内容”误当成“平台热点榜单”。

本轮已将采集策略升级为：

1. YouTube 官方体育榜单作为跨项目基线；
2. 50 个主流项目和 30 个一般项目分别执行真实项目检索；
3. 首次检索不足目标时，最多使用一个英文查询变体补采；
4. 同轮按平台外部视频 ID 去重，UI 展示真实返回量和不足原因；
5. 将平台的“已接入 / 需权限 / 待接入公开源”直接展示在热点覆盖卡片中。

## 为什么当前热点数不达标

- 之前 YouTube 只有 `search.list` 项目查询，没有使用官方体育分类榜单；
- 每个项目最多只发起一次查询，单个项目的有效结果可能低于目标；
- 同一视频可能同时命中多个项目检索，采集层为避免榜单重复只保留一条；
- TikTok、抖音和 Bilibili 当前已有账号或浏览器适配边界，但还没有统一接入全站热点榜单的合规 Provider；
- YouTube 的公开榜单与趋势含义并不完全相同。官方文档允许用 `videos.list` 的 `mostPopular` 按地区和视频分类读取榜单；YouTube 在 2025 年调整了 `mostPopular` 的内容范围，不能继续把它描述成旧版 Trending Now 的完整替代品。

## 已落地的采集改进

- `videos.list(chart=mostPopular, videoCategoryId=17)`：读取美国地区的官方体育分类榜单，最多 50 条；
- `videos.list(chart=mostPopular)`：通用榜单最多 50 条，作为跨项目补充；
- 项目检索：每个项目先执行配置的英文查询；低于目标时再执行 `highlights` 变体，最多两次查询；
- 统计增强：对返回的视频批量调用 `videos.list(part=snippet,statistics)`；统计不可用时保留真实搜索结果，但不伪造播放量；
- 结果解释：策略名称、来源方法和授权条件进入 `/trends/sports-catalog`，前端不再显示内部 taxonomy 版本号作为主信息。

## 主流平台接入边界

| 平台 | 当前边界 | 可行路径 | 本项目状态 |
|---|---|---|---|
| YouTube | 官方 API 可以读取地区/分类热门榜和项目检索结果 | Data API v3 + 有效 API Key + 配额预算 | 已接入热点采集 |
| TikTok | Display API 主要服务授权用户自己的视频；公共视频研究检索需要 Research API 权限 | Research API，或合法公开页面浏览器采集 | 需申请权限，未冒充全站趋势 |
| 抖音 | 账号开放平台权限不等于全站热点权限 | 对应开放平台热点能力，或合法公开页面浏览器采集 | 需应用权限，未冒充全站趋势 |
| Bilibili | 当前没有项目可以依赖的稳定官方全站热点 API 契约 | 公开热门榜页面浏览器采集，遇登录墙立即标记限制 | 待接入公开源 |

因此，答案是“可以分层采集”，但不能把四个平台都宣称成同等真实榜单：YouTube 现在具备官方榜单链路；TikTok 和抖音需要相应公共数据权限；Bilibili 需要先验证公开榜页面在当前网络和访问条件下可匿名读取。

## 后续优先级

### P0：来源覆盖

- 接入 Bilibili 公开热门榜浏览器 Provider，保存榜单 URL、抓取时间、页面排名和原始视频链接；
- 申请并配置 TikTok Research API，增加明确的公共视频检索字段契约；
- 核实抖音开放平台是否为当前应用授予热点/搜索权限，未满足时只展示条件提示。

### P1：配额与补采控制

- 为每个 Provider 增加每日配额预算、失败率、返回数量和每项目覆盖率；
- 只对低于目标的项目触发第二查询，避免 80 个项目每轮无条件翻倍请求；
- 将“Provider 返回量”“去重后唯一量”“最终写入量”分开记录，避免把去重损失误判成上游空数据。

### P2：质量提升

- 为每个项目维护赛事、联赛、球队和人物查询词，由“项目泛词”升级为“项目 + 当期事件”查询；
- 对跨项目命中的视频保存多项目标签，但在榜单中只保留一个规范视频实体；
- 增加榜单快照时间线，区分热度、播放量和新增速度，不把搜索排序直接命名为官方趋势。

## 数据真实性边界

系统不会为了满足 50/10 的数字创建重复或合成热点。若官方 Provider、公开页面或授权接口实际只能返回较少结果，页面会显示 `不足`，并给出对应来源条件。所有真实记录继续保留 `source_kind=live`、Provider、外部 ID、来源 URL 和采集时间。
